# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

"Roguelike Pool": a top-down 2D roguelike pool game for **mobile, portrait orientation**, built incrementally, one step at a time as the user asks. The user writes in French and UI text is French. The user tests in Play Mode after each step and expects an exact checklist of what to test. Current stage: a playable sandbox with a first stage loop. The table and the cue are the user's sprites (`pool_table.png`, `cue_stick.png`), with balls 1–10 racked (arcade set, ~56 % larger than regulation). The pockets are arcade: they help colored balls in and keep the cue ball out (see "Design intent: pocket difficulty"), and the user tunes each pocket's zones by hand in the Scene view. Aiming/shooting work, and the scratch rule applies (cue ball pocketed → shot cancelled). A stage loop (target score, shot limit, HUD, win/lose screens) runs over 6 stages. The game art is stylized pixel art. There are no game rules (groups, fouls) or roguelike systems yet.

### Design intent: pocket difficulty (user's words, 2026-11-17)
The user wants the game **accessible to everyone and "arcade"**, because real pool is hard: colored balls should go in easily, with a big margin and rebounds near pockets that help them in, while the cue ball should be hard to pocket. But scratching must stay *possible* when the cue ball is really aimed into a pocket: the goal is the "juste milieu" where avoiding a scratch feels rewarding without being frustrating. The current rule of thumb, checked by tests: **aim into the mouth → in; hit a jaw → out** for the cue ball, while colored balls also go in off the jaw. Keep any future pocket change measured with `JawTest` / `SideCueTest` (before/after numbers), and give the user the numbers.

### Last session (2026-11-17): steps 7 and 8
1. **Request 1:** colored balls easier with a bigger margin, cue ball even harder, rebounds near pockets that help colored balls, a more generous table hitbox around the pockets for the cue ball. → Step 7: bigger/smaller capture, aspiration, rebound funnel, cue-only corner and side guards. Measured with the new `JawTest`.
2. **User feedback:** "c'est vraiment bien, on approche de l'idéal", but the cue ball was **impossible to pocket in the side pockets** unless perfectly lined up, especially from an angle near a rail. They asked to loosen the hitbox **for the two side pockets only**.
3. **Diagnosis:** a bigger capture radius alone changed nothing. The side jaws are square, so a cue ball aimed at the pocket from near a rail hits the jaw tip head-on, and the step 7 side guard narrowed the mouth further. A cue ball hugging the rail also passes about 0.9 from the hole center, outside any reasonable capture radius.
4. **Fix (step 8):** removed the side guards, side cue capture 0.7, and cue-only beveled twins of the long-rail cushions (`sideCueBevel` 0.5). A cue rebound funnel was also tried (`sideCueFunnel`); it made jaw hits drop too, so it is off. A more generous variant (capture 0.9, bevel 0.8, funnel 0.4) let rail-hugging cue balls drop 4/9 but also swallowed most jaw hits, so it was rejected.
5. **Open question for the user:** should a cue ball rolling along the rail into a side pocket sometimes drop? Currently it never does. Step 8 hasn't been tried by the user yet.
6. **Test pitfalls hit this session (avoid repeating them):**
   - The first `JawTest` used speed 8 from far away: balls stopped before the rail (0/30, meaningless). Use speed 12 and the start points now in the script.
   - The `JawTest` parks the other balls bottom-left. A `PocketTest.Scratch` run right after hit those parked balls and looked like a regression. Restart Play Mode between test families.
   - `SideCueTest` first aimed at the hole center, which lies behind the rail line. At shallow angles the ball then hits the long rail long before the mouth. Aim at the mouth just inside the rail line, as a player would.
   - Async tests that run longer than 60 s need `--timeout 300`, or the run reports a timeout while the task keeps running detached.

## Architecture

- **Mostly built at runtime from code, except the table, the cue and the UI.** `Assets/Scenes/Pool.unity` (the only build scene) contains a Main Camera, the `UI` canvas (step 17), a `Game` object with `GameBootstrap` (it references `tablePrefab`, `cuePrefab`, the UI components, `tableFitter` and `pixelUpscaleShader`), and instances of the `PoolTable` and `Cue` prefabs (`Assets/Prefabs`), visible and editable in edit mode. `GameBootstrap` (execution order -1000) uses the scene instances, or instantiates the prefabs if none is in the scene, and creates the balls (`BallFactory`, 10-ball triangle), the shot UI, `TableRules`, `CueController` and the rendering/FX setup. The only user art is `Assets/Art/Sprites/pool_table.png` (1200×1800) and `cue_stick.png` (64×900), imported at PPU 67.7165 (felt width 860 px / 12.7 units), Bilinear, uncompressed, no mipmaps, Full Rect; table pivot = felt center, cue pivot = tip. Data assets: stages, `BallPhysicsSettings` and `Cushion.physicsMaterial2D` in `Assets/Data`.
- **Table/cue generator:** `Assets/Editor/TableSpriteBuilder.cs`, menu `Tools > Roguelike Pool` (also callable with `script eval`): 1 import sprites, 2 build the PoolTable prefab (overwrites it), 3 detect pockets in the PNG (moves only the pocket children), 4 (re)wire the PoolTable component without moving anything, 5 assign prefabs to GameBootstrap, 6 build the Cue prefab, 7 place both in the scene and frame the camera. All PNG measurements (felt edges, cushion ends) are constants at the top of the file, in pixels from the top-left. `AgentScripts/BuildPoolScene.cs` calls 5 and 7 after regenerating the scene.
- **Pixel art rendering (Dead Cells-inspired: dark cool palette, warm glowing accents).** The work is split by layer:
  - **World rendering:** `PixelCameraRig` renders the world at exactly `PixelArt.PPU` = 24 px/unit into a low-res RenderTexture (Bilinear) covering the screen. A RawImage shows it at `DisplayScale` screen px per art pixel (not an integer), chosen by `TableFitter` so the table fills `TableAnchor`, with the `PixelUpscale` sharp-bilinear shader keeping art pixels crisp (step 19). A separate `ScreenCamera` clears the real screen.
  - **Post-processing:** a global Volume created in code (`CreatePostProcessing`: bloom threshold 0.95, vignette, contrast). It runs at the low resolution. Don't use URP's PixelPerfectCamera: its upscale mode is incompatible with post-processing.
  - **Pointer input:** must go through `PixelCameraRig.ScreenToWorld`, not `Camera.ScreenToWorldPoint`. The inverse, `PixelCameraRig.WorldToScreen`, returns real screen pixels (used for the tangential aim drag).
  - **Art:** every texture is generated procedurally in `Assets/Scripts/Art`. **No dithering (user preference):** shapes stay pixel-crisp, but gradients are smooth (`PixelArt.Ramp` interpolates palette colors) and there is no per-pixel noise. Balls use clean 3-tone cel shading. `PixelArt` holds the palettes, ramps and noise. `PixelFont` holds the 5×7 UI font and the 3×5 ball digits. The table and the cue are the user's sprites (not generated); `TableArt` only builds the floor, the lamp spill and the table shadow around them. `BallArt` makes the 21 px balls plus their shadow. Art pixels map 1:1 to texels: ball sprites use PPU = 24 × diameter because the ball transform is scaled. Keep odd-sized sprites centered on pixel centers.
  - **Bloom:** glow = `PixelArt.GlowMaterial(hdrTint)` (Sprites/Default with an HDR `_Color`). Keep regular colors below the bloom threshold.
  - **FX:** `ImpactFX` (sparks and flash on ball-ball hits, triggered by `BallImpactFX` on each ball) and `AmbientMotes` (dust in the lamp light).
  - **UI:** uses the same pixel grid. The canvas is a scene object (`UI`, see step 17). Canvas Scaler: Scale With Screen Size 1080×1920, match 0.5, `referencePixelsPerUnit = 1`; one art pixel = `PixelUI.ArtPixel` (2) canvas units, generated sprites are drawn at rect / 2 and stretched (step 19). Set Image sizes explicitly, because `SetNativeSize` runs before the scaler applies its PPU. `PixelUI` generates the panel, button (SpriteSwap states, no label) and banner sprites; texts are TextMeshPro children whose words come from `GameTexts`. `PowerGauge` is drawn as an ARPG-style experience bar (user asked for a Diablo 3 XP bar feel). It is a brass-framed glass tube with a solid continuous fill: gloss strip, rising light sweep and bright leading edge. Ornate separators with brass studs sit at 25/50/75 %. The texture is redrawn every frame and laid over an invisible Slider. Its heat color shifts with the value, and above 85 % it adds a pulsing halo and UI pixel embers.
- **Scale: 1 world unit = 10 cm.** The table is in portrait: play area 12.7 × 21.65 units (sprite table) centered at the origin, long axis along Y. The head/cue ball is at the bottom (`HeadSpot`) and the rack apex at the top (`FootSpot`). The ball radius is 0.446875 (arcade: regulation 0.286 × 1.25 × 1.25).
- **Physics:** legacy Rigidbody2D. The project settings have 2D gravity set to 0, `bounceThreshold` 0.1, and a fixed timestep of 1/120. `Ball` uses zero built-in damping and applies cloth friction manually in `FixedUpdate` (constant deceleration + speed drag + snap-to-stop). `Ball.All` (active balls only) / `Ball.AllStopped` gate shooting. Physics materials use `Multiply` combine, so effective restitution = ball × cushion. `TrajectoryPreview` relies on this to predict the cushion bounce exactly, and it stops the line where the path enters a pocket (using that ball's capture radius, `Pocket.CaptureRadiusFor`).
- **Table and pockets:** the `PoolTable` prefab holds `Visual` (sprite on the `Table` sorting layer, below `Default`), `Cushions` (6 `PolygonCollider2D`, convention: points 0 → 1 = nose, 2 behind 1, 3 behind 0; 45° jaws), `Pockets` (`Pocket_TL/TR/ML/MR/BL/BR`, each a trigger `CircleCollider2D` kept equal to `Pocket.radius` by `OnValidate`, plus all the arcade values, editable by hand: the user wants to keep tuning them there), `RackPoint` and `CueBallSpawn`. The `PoolTable` component exposes these references, `playArea` (felt, 12.7 × 21.65, shorter than the old 25.4 because the sprite felt is 1.70:1) and `tableBounds` (opaque frame, for the camera and shadow), draws gizmos (felt, frame, safety walls, landmarks; each `Pocket` draws its own filled zones: yellow hole, green colored capture, red cue capture, and `Assets/Editor/PocketEditor.cs` adds, on the selected pocket, draggable dots for these three radii, dashed assist/funnel ranges and a values block) and at runtime adds `CueGuards` (corner guards and side bevel twins derived from the cushion ends, `RebuildCueGuards()` after a live change), `SafetyWalls` and `Surroundings` (`TableArt`: floor, lamp spill, shadow). Side pockets = pockets within a quarter of the play length from the center line. `Pocket` checks distances each `FixedUpdate` (the trigger is not used for capture; `TrajectoryPreview` ignores triggers): a ball whose center is within `CaptureRadiusFor(ball)` calls `Ball.FallInto`, which runs a short animation, deactivates the ball and raises the static `Ball.Pocketed` event. Pockets also register in the static `Pocket.Active` (reset on Play) and apply the arcade assists of step 7. Layers used by number, unnamed in the TagManager: 6 = cue ball, 7 = colored-only cushions. `TrajectoryPreview` casts with a layer mask that skips layer 7, so the preview matches the cue ball physics.
- **Cue:** the `Cue` prefab root `CueRoot` (`CueStick`) sits on the cue ball and turns with the aim (+X = shot direction); its child `Stick` holds the sprite (rotation offset -90°, tip pivot) and slides back by ball radius + `tipGap` + power pull-back; `Stick/Shadow` uses `WorldOffset`. `CueController` keeps all the aim/strike logic and calls `CueStick.Pose`.
- **Shot flow:** `CueController` reads `Pointer.current` (mouse in the Editor, touch on mobile). Drags are split along the cue axis: across = aim (constant sensitivity, eased), along = pull-back power (step 18); a tap aims at the tapped spot. The gauge slider also still sets the power. Fine aim comes from the UI toggle or Shift. Wheel/arrows change power, Space shoots. `Shoot()` calls `TableRules.TakeSnapshot()` before the strike. If the cue ball is pocketed, `TableRules` waits `restoreDelay`, then calls `Ball.ResetTo` on every ball in the snapshot. `Busy` blocks shooting meanwhile.
- **UI layout:** the user's mockup (step 19): settings button, stage title, score, money above the table; bonus tabs, power bar, TIRER and VISÉE FINE on the right; shot icons under the table; overlays in `UI/Overlays`. A message banner appears over the table. `ShotUI.IsOverUI` raycasts the canvas directly, which is reliable for touch.
- `AgentScripts/` (outside `Assets/`) holds editor builder/test scripts run with `unity command script run --file AgentScripts/X.cs --entry X.Run`:
  - `BuildPoolScene.cs` regenerates the scene.
  - `SetPortrait.Run(w, h)` adds/selects a portrait Game view size and sets the mobile orientation to Portrait. Use 540×960, the native art resolution at scale 1. In a Game view zoomed below 1×, Unity drops whole pixel rows/columns and small sprites like balls disappear; `GameViewFit.cs` sets the zoom to fit. `GameViewInfo.cs` reports the zoom.
  - `CropPng.Run(src, x, y, w, h, zoom, dst)` zooms into a screenshot, to inspect UI pixel art.
  - The rest are Play Mode tests: `ShotTest`, `PocketTest.Scratch/Break` and `CombinedScratchTest`, plus `CaptureMarginTest.Run(frac)` (drops a colored ball then the cue ball at frac × object capture radius from each pocket; 0.9 → objIn=True cueIn=False, 0.4 → both True; side pockets now have cue capture 0.788). `JawTest.Run(cue, speed)` (0 = colored ball 1, 1 = cue; use speed 12) fires 45 shots at the jaws and side mouths and counts pots; it parks the other balls bottom-left, so restart Play Mode afterwards. `ArcadeToggle.Run(0|1)` switches the step 7 assists off/on at runtime for A/B comparison. `SideCueTest.Run(capture, bevel, funnel, speed, colored)` sets the side cue values at runtime and shoots at the right side mouth from 27 positions (rows rail/near/far); reference: `[0.7, 0.5, 0, 9, 0]` → 16/27. `ArcadeToggle` only toggles the corner guards (never the `CueJawSide` twins, or the cue would pass through the long rails).
  - `CaptureArt.Run(x, y, w, h, zoom, path)` saves a nearest-neighbour zoom of the low-res world render, to inspect pixel art.
  - `BreakCaptureAll` captures a break at the moment of impact. `script run` accepts only one `--file`, so it is a merged copy that includes `CaptureArt`.
  - Capture screenshots with `capture game_view --width 1080 --height 1920`, since the default is 1280×720. For the real window, use `capture editor_window --window Game --output-path <file>` (the flag is `--output-path`, not `--save_path`).
  - Auto-tick is `unity command editor set_auto_tick --enabled true` (not `--enable`). A domain reload can drop the connection mid-command: re-check with `unity status --until-ready` rather than looping on `editor status`.
  - `CaptureArt` PNGs come out vertically flipped (texture rows are bottom-up). This is the capture, not the game.
  - After a recompile, wait until `editor status` shows no compile or domain reload before entering Play Mode. Otherwise the old code runs.
  - **Domain reload is disabled on Play** (Enter Play Mode Options): statics survive between Play sessions, but runtime-created Unity objects they reference are destroyed. Every static cache or registry needs a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset and a Unity null check (`BallArt`, `Ball`, `Pocket.Active` do this). Always test **two consecutive Play sessions**, and check the real window with `capture editor_window --window Game`: `capture game_view` re-renders and can hide such bugs.
  - Python is not installed on this machine.

## Engine and packages

- **Unity 6000.6.9f1** (see `ProjectSettings/ProjectVersion.txt`). Look up APIs for this version; don't assume older Unity behavior.
- **URP 17.6** with two quality tiers: `Assets/Settings/PC_RPAsset` + `PC_Renderer` and `Mobile_RPAsset` + `Mobile_Renderer`. Rendering changes usually need to go in both.
- **Input System only** (`activeInputHandler: 1`). The legacy `UnityEngine.Input` API will throw. Use `Assets/InputSystem_Actions.inputactions` (it ships with the template's Player/UI action maps) or `UnityEngine.InputSystem` directly.
- **uGUI** (`com.unity.ugui`) is installed. UI Toolkit is available as a built-in module.
- **`com.unity.pipeline`** is installed, so an agent can drive a running Editor: compile, run tests, eval C#, enter Play Mode, take screenshots. Use the `unity-pipeline` / `unity-cli` skills for these jobs instead of guessing at command-line flags.
- Physics: the game uses **2D physics only** (legacy Rigidbody2D). The 3D PhysX and 2D Physics Core modules are enabled but unused.
