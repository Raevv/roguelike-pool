# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

"Roguelike Pool": a top-down 2D roguelike pool game for **mobile, portrait orientation**, built incrementally, one step at a time as the user asks. The user writes in French and UI text is French. The user tests in Play Mode after each step and expects an exact checklist of what to test. Current stage: a playable sandbox. There is an American pool table with balls 1–10 racked (arcade set, ~56 % larger than regulation), arcade pockets that help colored balls in and keep the cue ball out (see "Design intent: pocket difficulty"), working pockets, aiming/shooting, and the scratch rule (cue ball pocketed → shot cancelled). Everything is in stylized pixel art. There are no turns, scoring, game rules or roguelike systems yet.

### Design intent: pocket difficulty (user's words, 2026-11-17)
The user wants the game **accessible to everyone and "arcade"**, because real pool is hard: colored balls should go in easily, with a big margin and rebounds near pockets that help them in, while the cue ball should be hard to pocket. But scratching must stay *possible* when the cue ball is really aimed into a pocket: the goal is the "juste milieu" where avoiding a scratch feels rewarding without being frustrating. The current rule of thumb, checked by tests: **aim into the mouth → in; hit a jaw → out** for the cue ball, while colored balls also go in off the jaw. Keep any future pocket change measured with `JawTest` / `SideCueTest` (before/after numbers), and give the user the numbers.

### Last session (2026-11-17): steps 7 and 8
1. **Request 1:** colored balls easier with a bigger margin, cue ball even harder, rebounds near pockets that help colored balls, a more generous table hitbox around the pockets for the cue ball. → Step 7: bigger/smaller capture, aspiration, rebound funnel, cue-only corner and side guards. Measured with the new `JawTest`.
2. **User feedback:** "c'est vraiment bien, on approche de l'idéal", but the cue ball was **impossible to pocket in the side pockets** unless perfectly lined up, especially from an angle near a rail. They asked to loosen the hitbox **for the two side pockets only**.
3. **Diagnosis:** a bigger capture radius alone changed nothing. The side jaws are square, so a cue ball aimed at the pocket from near a rail hits the jaw tip head-on, and the step 7 side guard narrowed the mouth further. A cue ball hugging the rail also passes about 0.9 from the hole center, outside any reasonable capture radius.
4. **Fix (step 8):** removed the side guards, side cue capture 0.7, and cue-only beveled twins of the long-rail cushions (`sideCueBevel` 0.5). A cue rebound funnel was also tried (`sideCueFunnel`); it made jaw hits drop too, so it is off. A more generous variant (capture 0.9, bevel 0.8, funnel 0.4) let rail-hugging cue balls drop 4/9 but also swallowed most jaw hits, so it was rejected.
5. **Open question for the user:** should a cue ball rolling along the rail into a side pocket sometimes drop? Currently it never does. Step 8 hasn't been tried by the user yet.
6. **Test pitfalls hit this session (avoid repeating them):**

## Architecture

- **Everything is built at runtime from code.** `Assets/Scenes/Pool.unity` (the only build scene) contains just a Main Camera and a `Game` object with `GameBootstrap` (its serialized `uiPanelFraction` = 0.2 overrides the code default). `GameBootstrap` creates the table, the balls (`BallFactory`, 10-ball triangle), the shot UI, `TableRules`, `CueController` and the rendering/FX setup. There are no prefabs or art assets. The only data assets are the stage ScriptableObjects in `Assets/Data` (step 9).
- **Pixel art rendering (Dead Cells-inspired: dark cool palette, warm glowing accents).** The work is split by layer:
  - **World rendering:** `PixelCameraRig` renders the world at exactly `PixelArt.PPU` = 24 px/unit into a point-filtered low-res RenderTexture. The texture is shown full screen by a RawImage at an integer `Scale`, the largest scale at which the table fits left of the panel. A separate `ScreenCamera` clears the real screen.
  - **Post-processing:** a global Volume created in code (`CreatePostProcessing`: bloom threshold 0.95, vignette, contrast). It runs at the low resolution. Don't use URP's PixelPerfectCamera: its upscale mode is incompatible with post-processing.
  - **Pointer input:** must go through `PixelCameraRig.ScreenToWorld`, not `Camera.ScreenToWorldPoint`. The inverse, `PixelCameraRig.WorldToScreen`, returns real screen pixels (used for the tangential aim drag).
  - **Art:** every texture is generated procedurally in `Assets/Scripts/Art`. **No dithering (user preference):** shapes stay pixel-crisp, but gradients are smooth (`PixelArt.Ramp` interpolates palette colors) and there is no per-pixel noise. Balls use clean 3-tone cel shading. `PixelArt` holds the palettes, ramps and noise. `PixelFont` holds the 5×7 UI font and the 3×5 ball digits. `TableArt` bakes the table into one texture: wood, felt, painted AO and lamp pool, cushions, brass pockets. It also builds the floor, the table shadow and the glowing diamonds. `BallArt` makes the 21 px balls plus their shadow, and `CueArt` the cue. Art pixels map 1:1 to texels: ball sprites use PPU = 24 × diameter because the ball transform is scaled. Keep odd-sized sprites centered on pixel centers.
  - **Bloom:** glow = `PixelArt.GlowMaterial(hdrTint)` (Sprites/Default with an HDR `_Color`). Keep regular colors below the bloom threshold.
  - **FX:** `ImpactFX` (sparks and flash on ball-ball hits, triggered by `BallImpactFX` on each ball) and `AmbientMotes` (dust in the lamp light).
  - **UI:** uses the same pixel grid. `ShotUI` canvas: ConstantPixelSize with `scaleFactor = rig.Scale`, and `referencePixelsPerUnit = 1`, so 1 canvas unit = 1 art pixel. Set Image sizes explicitly, because `SetNativeSize` runs before the scaler applies its PPU. `PixelUI` holds the panel, buttons (SpriteSwap states with baked labels), banner and text. `PowerGauge` is drawn as an ARPG-style experience bar (user asked for a Diablo 3 XP bar feel). It is a brass-framed glass tube with a solid continuous fill: gloss strip, rising light sweep and bright leading edge. Ornate separators with brass studs sit at 25/50/75 %. The texture is redrawn every frame and laid over an invisible Slider. Its heat color shifts with the value, and above 85 % it adds a pulsing halo and UI pixel embers.
- **Scale: 1 world unit = 10 cm.** The table is a 9ft table in portrait: play area 12.7 × 25.4 units centered at the origin, long axis along Y. The head/cue ball is at the bottom (`HeadSpot`) and the rack apex at the top (`FootSpot`). The ball radius is 0.446875 (arcade: regulation 0.286 × 1.25 × 1.25).
- **Physics:** legacy Rigidbody2D. The project settings have 2D gravity set to 0, `bounceThreshold` 0.1, and a fixed timestep of 1/120. `Ball` uses zero built-in damping and applies cloth friction manually in `FixedUpdate` (constant deceleration + speed drag + snap-to-stop). `Ball.All` (active balls only) / `Ball.AllStopped` gate shooting. Physics materials use `Multiply` combine, so effective restitution = ball × cushion. `TrajectoryPreview` relies on this to predict the cushion bounce exactly, and it stops the line where the path enters a pocket (using that ball's capture radius, `Pocket.CaptureRadiusFor`).
- **Table and pockets:** `PoolTable` builds 6 trapezoid cushions (`PolygonCollider2D`) cut at the pockets, with 45° corner jaws, plus safety walls at the outer rail edge. `Pocket` checks distances each `FixedUpdate` (no triggers): a ball whose center is within `CaptureRadiusFor(ball)` calls `Ball.FallInto`, which runs a short animation, deactivates the ball and raises the static `Ball.Pocketed` event. Pockets also register in the static `Pocket.Active` (reset on Play) and apply the arcade assists of step 7. `CueGuards` (child of the table) holds the cue-only colliders (`CueGuardCorner` ×8, `CueJawSide` ×4). Layers used by number, unnamed in the TagManager: 6 = cue ball, 7 = colored-only cushions. `TrajectoryPreview` casts with a layer mask that skips layer 7, so the preview matches the cue ball physics.
- **Shot flow:** `CueController` reads `Pointer.current` (mouse in the Editor, touch on mobile). Aim is relative (tangential drag around the cue ball, constant sensitivity, eased), a tap aims at the tapped spot. Fine aim comes from the UI toggle or Shift. Wheel/arrows change power, Space shoots. `Shoot()` calls `TableRules.TakeSnapshot()` before the strike. If the cue ball is pocketed, `TableRules` waits `restoreDelay`, then calls `Ball.ResetTo` on every ball in the snapshot. `Busy` blocks shooting meanwhile.
- **UI layout:** the right `uiPanelFraction` (0.2) of the screen holds the FORCE gauge, VISÉE FINE and TIRER. A message banner appears over the table. `ShotUI.IsOverUI` raycasts the canvas directly, which is reliable for touch.
- `AgentScripts/` (outside `Assets/`) holds editor builder/test scripts run with `unity command script run --file AgentScripts/X.cs --entry X.Run`:
  - `BuildPoolScene.cs` regenerates the scene.
  - `SetPortrait.Run(w, h)` adds/selects a portrait Game view size and sets the mobile orientation to Portrait. Use 540×960, the native art resolution at scale 1. In a Game view zoomed below 1×, Unity drops whole pixel rows/columns and small sprites like balls disappear; `GameViewFit.cs` sets the zoom to fit. `GameViewInfo.cs` reports the zoom.
  - `CropPng.Run(src, x, y, w, h, zoom, dst)` zooms into a screenshot, to inspect UI pixel art.
  - The rest are Play Mode tests: `ShotTest`, `PocketTest.Scratch/Break` and `CombinedScratchTest`, plus `CaptureMarginTest.Run(frac)` (drops a colored ball then the cue ball at frac × object capture radius from each pocket; 0.9 → objIn=True cueIn=False, 0.4 → both True; side pockets now have cue capture 0.788). `JawTest.Run(cue, speed)` (0 = colored ball 1, 1 = cue; use speed 12) fires 45 shots at the jaws and side mouths and counts pots; it parks the other balls bottom-left, so restart Play Mode afterwards. `ArcadeToggle.Run(0|1)` switches the step 7 assists off/on at runtime for A/B comparison. `SideCueTest.Run(capture, bevel, funnel, speed, colored)` sets the side cue values at runtime and shoots at the right side mouth from 27 positions (rows rail/near/far); reference: `[0.7, 0.5, 0, 9, 0]` → 16/27. `ArcadeToggle` only toggles the corner guards (never the `CueJawSide` twins, or the cue would pass through the long rails).
  - `CaptureArt.Run(x, y, w, h, zoom, path)` saves a nearest-neighbour zoom of the low-res world render, to inspect pixel art.
  - `BreakCaptureAll` captures a break at the moment of impact. `script run` accepts only one `--file`, so it is a merged copy that includes `CaptureArt`.
  - Capture screenshots with `capture game_view --width 1080 --height 1920`, since the default is 1280×720. For the real window, use `capture editor_window --window Game --output-path <file>` (the flag is `--output-path`, not `--save_path`).
  - Auto-tick is `unity command editor set_auto_tick --enabled true` (not `--enable`). A domain reload can drop the connection mid-command: re-check with `unity status --until-ready` rather than looping on `editor status`.
  - `CaptureArt` PNGs come out vertically flipped (texture rows are bottom-up). This is the capture, not the game.
  - After a recompile, wait until `editor status` shows no compile or domain reload before entering Play Mode. Otherwise the old code runs.
  - **Domain reload is disabled on Play** (Enter Play Mode Options): statics survive between Play sessions, but runtime-created Unity objects they reference are destroyed. Every static cache or registry needs a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset and a Unity null check (`BallArt`, `Ball`, `Pocket.Active` do this). Always test **two consecutive Play sessions**, and check the real window with `capture editor_window --window Game`: `capture game_view` re-renders and can hide such bugs.
  - Python is not installed on this machine.

## Engine and packages

- **Unity 6000.6.9f1** (see `ProjectSettings/ProjectVersion.txt`). Look up APIs for this version; don't assume older Unity behavior.
- **URP 17.6** with two quality tiers: `Assets/Settings/PC_RPAsset` + `PC_Renderer` and `Mobile_RPAsset` + `Mobile_Renderer`. Rendering changes usually need to go in both.

- Physics: the game uses **2D physics only** (legacy Rigidbody2D). The 3D PhysX and 2D Physics Core modules are enabled but unused.

## Conventions

- Version control is git with Unity's standard `.gitignore` (`Library/`, `Temp/`, `Logs/`, `UserSettings/` are ignored). Always commit `.meta` files alongside their assets, and never hand-edit GUIDs.
- Scenes, prefabs, and `.asset` files are YAML. Prefer making changes through Editor scripts or the Editor itself over hand-editing serialized YAML.
